# 리소스별 임계치 편집 · 벌크 Configure Alarms — 디자인 초안

상태: 초안(2026-11-03), 승인 전 구현하지 않음.

## 1. 문제

- 리소스 상세의 알람 편집(`PUT /resources/{id}/alarms`)은 중앙 계정 자격 증명으로 CloudWatch를 고친다. 고객 계정(HOME)
  리소스에 쓰면 알람이 중앙 계정에 생기고, 태그는 EC2만 쓴다. EC2가 아닌 타입은 매시 정합 런이 변경을 되돌린다.
  HOME에서는 한 번도 쓰인 적이 없다(남은 알람 0개 확인).
- 벌크 버튼은 `Configure Alarms (예정)`으로 비활성 상태다.

## 2. 결정 사항(확정)

- 리소스별 값은 **고객 리소스의 `Threshold_*` 태그**에 둔다(방식 B). 온보딩 역할은 `30ac2b6`부터
  `Monitoring`·`Threshold_*` 키를 쓰고 지울 수 있다. HOME 스택도 업데이트 완료.
- 우선순위는 그대로: 리소스 태그 → 고객사 기본값 → 시스템 기본값.

## 3. 동작

**하나의 경로**로 단일 편집과 벌크를 모두 처리한다.

1. 고객 계정 세션(모니터링 토글과 같은 세션)으로 태그를 쓴다. 값 지정은 `Threshold_{지표}=값`, 개별값 해제는 태그 삭제,
   알람 끄기는 `Threshold_{지표}=off`.
2. 바뀐 태그로 그 리소스의 알람을 즉시 다시 만든다. 토글 ON과 같은 함수를 쓰고, 고객사 기본값도 같은 규칙으로 끼운다.
   그래서 데일리 런과 같은 결과가 나온다.
3. 인벤토리 알람 행을 갱신한다. 실패해도 다음 정합 런이 맞춘다.

**판단 방식(M/N, 11-03 추가):** `Threshold_{지표}_Eval=M/N` 태그로 지표마다 바꿀 수 있다(1 ≤ M ≤ N ≤ 10).
없으면 지금처럼 심각도 기반 정책을 쓴다. 기간·통계는 지표 의미가 바뀌므로 열지 않는다. 가용성 지표(SEV-1,
누락=위반)는 1/1 고정이다. 화면에는 "최근 25분 중 15분 이상"처럼 풀어서 보여준다. 비용 변화는 없다(알람 수 동일).

**범위:** 임계치·판단 방식(그리고 끄기)만 다룬다. 심각도·기간 같은 나머지 설정은 태그 계약에 없어서, 바꿔도 정합 런이 되돌린다.
그래서 편집 화면에서 뺀다.

### API(신규)

| | 요청 | 응답 |
|---|---|---|
| `GET /resources/{id}/thresholds` | — | 지표마다 `{metric, label, unit, value, source: resource\|customer\|system, customer_default, system_default}` |
| `PUT /resources/{id}/thresholds` | `{set: {지표: 값\|"off"}, clear: [지표]}` | `{status, tags_written, tags_removed, alarms}` 또는 오류(`ACCESS_DENIED`면 "고객사 스택 업데이트 필요" 안내) |

기존 `PUT /resources/{id}/alarms`는 새 경로로 위임하고, 임계치 외 필드는 무시한다.

## 4. 화면

### 4.1 리소스 상세 > 알람 — 단일 편집

```
┌ 임계치 ───────────────────────────────────────────────────────┐
│ 지표              현재값     출처         새 값                │
│ CPU 사용률        80 %      시스템 기본    [ 90 ] %           │
│ 메모리 사용률      85 %      고객사 기본    [    ] %  (비우면 유지) │
│ 디스크 / 사용률    70 %      개별값 ●      [ 70 ] %  [개별값 해제] │
│ 상태 검사          —         시스템 기본    [ 끄기 ▢ ]          │
├───────────────────────────────────────────────────────────────┤
│ ⓘ 값을 넣으면 이 리소스에 고정됩니다. 고객사 기본값을 바꿔도      │
│   따라가지 않습니다. 따라가게 하려면 [개별값 해제]를 누르세요.   │
│                                         [취소]  [저장]         │
└───────────────────────────────────────────────────────────────┘
```

- 출처 배지: `개별값`(파랑), `고객사 기본`(회색), `시스템 기본`(연회색).

### 4.2 리소스 목록 — 벌크 Configure Alarms

진입: 같은 타입 리소스를 여러 개 고른 뒤 `Configure Alarms`를 누른다. 타입이 섞이면 지금처럼 비활성이고 이유를 보여준다.

**1단계: 바꿀 값**

```
┌ 알람 설정 — EC2 12개 ────────────────────────────────────────┐
│ 지표              새 값                동작                  │
│ CPU 사용률        [ 90 ] %            ◉ 값 지정  ○ 개별값 해제 │
│ 메모리 사용률      [    ]              (손대지 않음)           │
│ 디스크 / 사용률    [    ]              (손대지 않음)           │
│                                          [취소]  [영향 보기 →] │
└──────────────────────────────────────────────────────────────┘
```

**2단계: 영향 보기(적용 전)**

```
┌ 영향 — CPU 사용률 ───────────────────────────────────────────┐
│ 12개 중  바뀜 9 · 이미 같음 2 · 끈 알람 1(건너뜀)              │
│                                                              │
│ 리소스            현재          →  적용 후                    │
│ web-01           80 시스템      →  90 개별값                  │
│ web-02           85 고객사      →  90 개별값                  │
│ batch-01         95 개별값      →  90 개별값   ⚠ 기존 개별값 덮어씀 │
│ db-proxy         90 개별값      →  (변화 없음)                 │
│ legacy-01        off           →  건너뜀(끈 알람은 그대로)     │
│ …                                                            │
│ ⓘ 적용하면 9개 리소스에 값이 고정됩니다.                        │
│                                  [← 뒤로]  [9개 적용]          │
└──────────────────────────────────────────────────────────────┘
```

- `⚠ 기존 개별값 덮어씀`은 따로 센다. 기본은 덮어쓰고, 체크를 풀면 그 리소스는 제외한다.
- 끈 알람(`off`)은 값 지정으로 다시 켜지 않는다. 다시 켜는 건 단일 편집에서만 한다.

**3단계: 적용 결과**

```
┌ 적용 결과 ───────────────────────────────────────────────────┐
│ ████████████░░  9개 중 8 성공 · 1 실패                          │
│ ✕ batch-03   권한 없음 — 고객사 스택 업데이트가 필요합니다        │
│                                  [실패만 재시도]  [닫기]         │
└──────────────────────────────────────────────────────────────┘
```

- 리소스당 요청 하나, 동시에 3개씩 보낸다. 창을 닫아도 이미 보낸 요청은 계속 처리된다.

## 5. 남은 결정

- 영향 보기 계산 위치: 화면에서 리소스마다 `GET …/thresholds`를 부르는 방식(추천, 별도 API 없음)과 미리보기 API 하나를
  새로 만드는 방식 중 무엇으로 할지.
- 디스크 경로별 지표(`/data` 등) 포함 여부: 1차에서는 단일 편집에서만 다루고 벌크에서는 뺀다(추천).

## 6. 검증 계획

- 단위: 태그 쓰기·삭제 요청 형태, 출처 계산, 끈 알람 건너뛰기, `AccessDenied` 안내.
- 라이브: 중앙 계정 리소스로 먼저 시험한다. 고객 리소스로 시험하지 않는다는 원칙을 따른다. HOME은 승인을 받은 뒤
  리소스 하나로 값 지정과 해제를 한 번씩만 해본다.
