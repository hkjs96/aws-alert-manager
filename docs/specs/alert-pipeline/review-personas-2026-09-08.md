## 페르소나 1 — 온콜 SRE (알림을 받는 사람)

"억제가 진짜 장애를 숨기는가"만 본다.

- **fail-open 일관성**: 상태·그룹·설정 어느 것이 죽어도 NOTIFY로 빠진다. 합격.
- **F4 그룹 고착**: 워커가 3회 재시도 후에도 실패하면 실행은 FAILED로 끝나지만 `grp#`
  항목은 `status=open` + `execution_arn` 그대로다. `_resolve_group`은 열린 그룹이면 무조건
  합류시키므로, 이후 같은 `{customer}#{severity}` 이벤트는 죽은 그룹에 계속 붙는다.
  TTL(1일)까지 아무도 확정하지 않는다 → **Phase 2에서는 하루치 알림이 통째로 사라진다.**
  `AlertGroupWorkerErrorsAlarm`이 울리긴 하지만 사람이 손으로 풀어야 한다.
  - 처방: `_resolve_group`에서 `opened_at + group_wait_sec + grace + 최대 pause + 여유(예 5분)`를
    넘긴 열린 그룹은 stale로 보고 새 그룹을 연다(조건부 put이라 경합 안전). 워커
    `finalize`는 stale 처리된 옛 그룹의 멤버를 `final_action=notify, reason=stale_group`으로
    write-back 하는 청소 액션이 필요하다. 지금은 기록만 하므로 안전하지만 발송 전 필수.
- **flapping 격리 1시간**: SEV-2 리소스가 임계치 언저리에서 진동하면 1시간 조용해진다.
  설계상 의도이고 SEV-1은 면제. 다만 F7 때문에 고객이 격리 사실을 볼 수 없다.
- **dedup 15분**: CloudWatch는 전이만 내보내므로 "15분 안 재발화"는 곧 진동이다. 타당.

## 페르소나 2 — 보안 검토자

- **F1 태그·설명 불일치**: ALARM-RULES는 태그가 정본이라 하지만 파이프라인은 설명을 읽는다.
  두 저장소가 갈라지는 경로가 우리 코드 안에 둘 있다.
  - `api_handler/routes/resources.py:345` 커스텀 알람 생성: 사용자가 고른 `severity`를
    태그(364행)에는 쓰지만 `_build_alarm_description`에는 넘기지 않는다 → 설명은 레지스트리 기본값.
  - `resources.py:851 _update_metric_alarm` 등급 변경: `_metric_alarm_update_kwargs`가
    기존 `AlarmDescription`을 그대로 복사하고 태그만 새 등급으로 바꾼다 → 설명은 옛 등급.
  - 결과: UI에서 SEV-1로 올린 알람이 파이프라인에는 SEV-3으로 보이고 **SEV-1 면제가 적용되지
    않는다.** P2가 막으려던 바로 그 실패다. 앞선 보고의 "태그와 설명이 어긋날 일은 없다"는
    자동 생성 경로에만 맞는 말이었다.
  - 처방: (a) 345행에 `severity=severity` 전달, (b) update kwargs에서 설명의 severity를 config
    값으로 다시 쓰기(메타데이터 JSON만 교체, human_prefix 보존), (c) "Severity 태그를 쓰는 모든
    경로는 설명에도 쓴다"를 테스트로 고정.
- **F2 값 검증 없음**: `identify_alarm`은 `str(metadata.get("severity"))`를 그대로 쓴다.
  고객 계정에서 설명을 손으로 고쳐 `"severity":"urgent"`를 넣으면 이력·group_key에 그대로
  들어간다. 자기 알람의 우선순위만 바꾸는 것이라 위협은 낮지만 데이터 품질 문제다.
  - 처방: `SEV-1`~`SEV-5` 허용 목록 밖이면 비우고 레지스트리 폴백.
- 설명은 `cloudwatch:PutMetricAlarm` 권한이면 누구나 바꾼다. 태그도 마찬가지라 신뢰 경계는
  P2 이전과 같다. 추가 위험 없음.
- 버스 정책 `events:source` 조건 부재, 온보딩 템플릿 권한은 1.2.2에서 같이 본다(기존 목록).

## 페르소나 3 — 운영·비용 (FinOps + 유지보수)

- **F3 기존 알람 미갱신**: `alarm_sync._CONFIG_FIELDS`는 Statistic/Period/EvaluationPeriods/
  ComparisonOperator/TreatMissingData/DatapointsToAlarm만 비교한다. 설명에 severity가 없는
  옛 알람은 다른 설정이 바뀌기 전엔 영원히 폴백 경로다. 자동 생성 알람은 폴백 = 태그라
  무해하지만, UI에서 등급을 바꾼 알람은 F1과 같은 불일치가 남는다.
  - 처방: 동기화 시 "설명에 severity 없음"을 드리프트로 취급해 재생성(PutMetricAlarm ~3 TPS라
    점진적). 별도 백필 스크립트보다 싸고 자동이다.
- **F6 비용**: 그룹 1개 = 실행 1개 ≈ 7~8 전이. 1,000그룹/일이면 월 약 $6. 고객·등급당
  30초에 하나가 상한이므로 폭주해도 유계이지만, 실측 없이는 예산을 못 잡는다. `alert_group`
  PERF_METRIC으로 1.2.2 후 1주 세어 본다.
- 예약 동시성 50+20은 계정 풀(1,000)에서 빠진다. 다른 함수에 영향 없는 수준.
- `desc[:1024]` 절단: 접두어 + JSON이 1024자를 넘으면 JSON이 잘려 파싱 실패 → 이름 폴백.
  현재 접두어 최대 ~120자, 리소스 ID 최대 ~200자라 도달하지 않는다. 기록만.

## 페르소나 4 — 제품 (고객 관점)

- **F7**: 억제·그룹 결과가 이력 행에만 있고 화면에 없다. Phase 2에서 발송이 시작되면
  "알람은 울렸는데 Slack엔 안 왔다"가 첫 문의가 된다. 이력 화면에 final_action/final_reason,
  격리 종료 시각, 활성 정비창 목록이 같이 나가야 한다. 발송보다 먼저 만들어도 된다.
- 진입 조건 자체(멱등성, 등급 출처)는 고객에게 보이지 않는 기반 작업이다. 타당.
- 실질 가치는 1.2.2(고객 계정 수집)에 걸려 있다. 그 전까지 모든 억제 통계는 우리 계정 셀프
  테스트다. Phase 0 측정도 그 뒤다. 자동 유예 기본값이 비어 있는 건 옳다.

## 페르소나 5 — 회의적인 시니어 리뷰어

- **P1 검증**: 상태 → 그룹 → 이력 순서. 이력 조건 실패 시 상태는 이미 두 번 반영됐지만
  `apply_event`는 집합·가드 기반이라 결과가 같다(확인: `_episodes_in_window` set,
  `episode_open` 가드, 두 번째는 dedup이라 `last_notified_at` 불변). 합격.
- **알려진 지연 경로**: 1차 처리가 StartExecution 뒤·이력 put 전에 죽으면 멤버가 그룹에
  없다. 재시도가 finalize 뒤에 오면 새 그룹을 열어 늦게라도 보낸다. 유실은 아니다. 문서화만.
- **F5**: `customer_id`가 빈 계정은 group_key가 `#SEV-x`다. 지금은 우리 계정뿐이라 무해하나
  1.2.2 뒤 미등록 계정 알림이 서로 섞인다. 미등록 계정은 그룹 없이 바로 NOTIFY로 빼거나
  account_id로 키를 잡는다.
- **테스트 사각**: P2 테스트는 `_build_alarm_description`과 인제스터만 봤고 UI 경로를
  안 봤다. 그래서 F1이 통과했다. 경로별 단위 테스트보다 "Severity 태그 쓰는 곳 = 설명 쓰는
  곳" 불변식을 검사하는 테스트가 재발을 막는다.
- 인제스트 룰 DLQ, 상태 머신 Task Retry(3회) 있음. 합격.

## 처리 결과 (2026-09-08, dev v20260908T041030)

- **F1** `set_description_severity()` 추가. 커스텀 알람 생성은 고른 등급을 설명에도 쓰고, 등급 변경은 기존 설명의
  메타데이터만 바꿔 접두어를 보존한다. 정적 검사 테스트가 "Severity 태그를 쓰는 함수 = 설명을 만드는 함수"를 고정한다
  (`tests/test_severity_consistency.py`).
- **F2** `is_valid_severity()` — 설명 파싱은 SEV-1~5 밖이면 버리고 레지스트리 폴백, API 입력은 400.
- **F3** 동기화가 설정은 맞지만 설명에 등급이 없는 알람을 `refreshed`로 표시하고, 끝에 제자리 `put_metric_alarm`으로
  설명만 채운다. 값은 Severity 태그 우선(UI 변경 보존), 없으면 레지스트리. 재생성이 아니므로 상태·이력·태그가 유지된다.
  알람당 describe + list_tags + put 3호출, 1회성. dev에는 관리 알람이 0개라 갱신 물량은 없다(자기 감시 알람 6개는 비관리).
  재생성 대신 제자리 갱신을 택한 이유: 재생성은 상태·이력을 지우고 F8 때문에 태그까지 되돌린다.
- **F9** `_alarm_arn_for_name`을 `:alarm:` 구분자로 자르도록 수정. 단위 테스트가 mock ARN만 검사해 지금까지 통과했다.
- **F8** 손대지 않았다. 레지스트리 기본값이 수동 등급을 이겨야 하는지는 제품 결정이다. 결정 전까지 UI에서 바꾼 등급은
  다음 드리프트 재생성 때 사라질 수 있다.
- 라이브 검증(dev): F3 — 옛 형식 설명 + 태그 SEV-2 알람을 ALARM 상태에서 갱신 → 설명 SEV-2, 접두어·상태·태그·설정 전부
  유지, 두 번째 호출은 no-op. F1 — 등급 변경 SEV-1 → 태그·설명 모두 SEV-1(F9 수정 전엔 태그가 SEV-2로 남았다).
  F2 — 설명 `"severity":"urgent"` 이벤트 → 배포된 인제스터가 이력에 SEV-3(레지스트리). 로그에 AccessDenied 없음.
  전체 테스트 2,160건 통과.

## 처리 결과 2차 (2026-09-08, dev v20260908T063707)

- **F8** 사용자 결정: **수동 등급이 레지스트리 기본값을 이긴다.** 재생성 경로 셋(이름별 `_recreate_alarm_by_name`,
  전체 `create_alarms_for_resource`, 동적 드리프트)이 지우기 전에 Severity 태그를 읽어(`_severity_overrides`,
  기본값과 다를 때만) 새 알람의 태그와 설명에 그대로 쓴다. 인덱스 스냅샷처럼 ARN이 없으면 이름으로 만든다.
  라이브: 태그 SEV-1 알람을 재생성 → 새 알람 태그·설명 모두 SEV-1.
- **F4** 두 겹. ① EventBridge 실행 상태 변경(FAILED/TIMED_OUT/ABORTED) 룰 → 워커 `sweep`: 열려 있으면 닫고 유예 없이
  finalize(이미 확정된 구성원 건너뜀, `final_reason`에 `swept:<status>`). 상태 머신 `TimeoutSeconds` 7200.
  ② 인제스터는 `opened_at + group_wait_sec + 300s`를 넘긴 열린 그룹을 고착으로 보고 새 그룹을 연다(`stale_group=true`,
  PERF_METRIC 필드). 라이브: 실행을 ABORTED로 끊자 워커가 구성원 2건을 `notify/swept:aborted`로 확정하고 grp#를
  닫았다(실행 ARN 부재 없이 이벤트의 `detail.input`이 곧 그룹). 20분 전에 연 가짜 열린 그룹에 이벤트를 넣자 인제스터가
  새 그룹·새 실행을 열었다. 옛 그룹 `close`는 group_id 조건이 있어 새 그룹을 덮지 않는다.
- 전체 테스트 2,182건 통과. 로그에 AccessDenied 없음.
- **F5** `group_key`가 `customer_id or account_id`로 대체한다 — 미등록 계정끼리 뭉치지 않는다.
  1.2.2(버스 정책 자동화)로 등록된 계정만 이벤트를 보낼 수 있게 됐지만, 등록과 매핑 캐시(60초) 사이의
  창과 매핑 조회 실패(fail-open)에서 여전히 빈 customer_id가 나온다.
- 남은 것: F6(비용 실측)·F7(억제 사유 UI) — Phase 2.
