# 알림 채널 설계 — 확장 규칙 (2026-09-09)

Phase 2.2의 뼈대. **채널 유형을 늘리는 일이 파일 하나 추가로 끝나야 한다**는 요구에서 출발했다.
관련: design.md D3(채널은 DB 표)·D7(자격증명 저장), tasks.md 2.2.

## 무엇이 확장되는가

두 축이 따로 늘어난다. 섞으면 둘 다 어려워진다.

| 축 | 늘어나는 예 | 늘리는 방법 |
|---|---|---|
| **채널 유형** | Slack → Teams, Discord, SMS, PagerDuty | `notification_adapters.py`에 `Adapter(...)` 블록 하나 |
| **조건 축** | 등급·리소스타입·계정 → 시간대, 리전 | `MATCH_FIELDS`에 이름 추가 + 이벤트에서 같은 키를 읽기 |

## 채널 유형 = 어댑터 하나

어댑터가 스스로 선언한다. 라우터·검증·API 응답 필터는 이 선언을 읽을 뿐 유형을 알지 못한다.

```python
TEAMS = register(Adapter(
    type="teams",
    label="Microsoft Teams",
    fields=(Field("webhook_url", "Webhook URL", secret=True, check=_https_url),),
    render=_render_teams,
    rate_limit_per_sec=4.0,
))
```

이걸 더하면 다음이 **자동으로** 따라온다.

- 입력 검증 (필수 여부·길이·형식)
- 모르는 설정 키 거절
- **API 응답에서 자격증명 제거** — `secret=True` 선언 하나가 근거다
- 유형 목록 API·설정 화면의 선택지
- 발송 속도 상한
- `tests/test_notification_channel.py::TestEveryAdapter`의 계약 검사 5종

마지막 항목이 핵심이다. 새 어댑터는 테스트를 새로 쓰지 않아도 "필드를 선언했는가",
"렌더가 빈 페이로드를 내지 않는가", "자격증명이 응답에 새지 않는가"를 자동으로 검사받는다.

### 자격증명은 기억이 아니라 구조로 막는다

`api_handler`에는 스캔 결과를 그대로 응답에 넣는 코드가 12곳 있다(R6-8 경고). 채널 API가 그
관례를 따르면 슬랙 웹훅 URL이 목록 응답으로 샌다. 그래서 **응답 직렬화가 검증과 같은 선언을
읽도록** 했다. `channel_to_dict()`는 필드를 하나씩 훑으며 `secret`이면 값 대신 `"(설정됨)"`을
넣는다. 새 어댑터가 값을 흘리려면 secret 표시를 빠뜨려야 하는데, 그건 계약 테스트가 잡는다.

저장은 그대로 한다 — 안 그러면 보낼 수 없다(D7: 별도 시크릿 저장소 없음).

## 고객사는 조건이 아니라 키다

```
NotificationChannelTable   PK customer_id / SK channel_id
  customer_id = ""  →  전역 채널(모든 고객사, 우리 관제 채널용)
```

조건(`match`)은 **한 고객사 안에서만** 범위를 좁힌다. 이렇게 나눈 이유는 실패 모드가 다르기
때문이다. 조건 처리에 버그가 나면 소음이 늘 뿐이지만, 고객사 경계가 조건이었다면 같은 버그가
**A사 알림을 B사 채널로 보낸다.** 경계는 조회 키가 지키고, 조건은 그 안에서만 논다.

## 조건은 "비면 전부"인 목록

```json
{ "severity": ["SEV-1", "SEV-2"], "resource_type": ["RDS"] }
```

- 축이 없거나 비면 그 축은 걸지 않는다 → **새 축을 더해도 기존 행은 그대로 동작한다.**
  마이그레이션이 필요 없다.
- 축끼리는 AND, 축 안의 값끼리는 OR.
- **모르는 축은 저장 단계에서 거절한다.** 조용히 버리면 사용자는 "RDS만"이라고 저장했다고 믿는데
  실제로는 전부 받는다. 저장을 막으면 라우터가 모르는 축을 만날 일이 없다.
- 그럼에도 옛 행에 모르는 축이 남아 있으면 라우터는 그 축을 무시한다. 좁히지 못할 뿐이고,
  고객사 경계는 키가 지키므로 새지 않는다.

## 알림 본문은 한 번만 만든다

라우터가 이벤트를 `Notification` 하나로 바꾸고, 어댑터는 그것만 보고 그린다. 어댑터가 이벤트
원본을 파싱하지 않으므로 이력 항목 구조가 바뀌어도 어댑터를 고치지 않는다.
묶음 발송(폭풍 시 요약)도 같은 구조다 — `count > 1`이면 대표 1건 + "외 N건".

## 결정 근거로 남길 것

- **U2(등록 주체)**: 우리가 대행. 고객사 직접 등록은 고객사 로그인·권한 체계가 선행이라
  실제 고객 데이터가 들어오기 전에 지을 순서가 아니다. 이 설계는 그 전환을 막지 않는다 —
  채널 행이 이미 고객사별로 나뉘어 있어, 나중에 고객사 인증이 생기면 조회 범위만 좁히면 된다.
- **U3(조건 범위)**: 등급 + 리소스타입 + 계정. 셋 다 이벤트에 이미 있는 값이라 추가 비용이
  없다. 시간대는 축을 하나 더하는 일이므로 요청이 나오면 그때 넓힌다.
