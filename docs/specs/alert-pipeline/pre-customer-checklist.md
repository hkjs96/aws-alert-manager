# 고객사 배포 전 점검 (2026-09-08)

첫 고객사 계정에 온보딩 스택을 배포하기 전에 실제 상태를 점검하고 고친 것들.
"코드가 있다"와 "고객에게 내보낼 수 있다"는 다르다.

## 처리한 것

| # | 발견 | 심각도 | 상태 |
|---|---|---|---|
| P1 | **온보딩 템플릿이 존재하지 않는 prod 버스를 기본값으로 가리켰다** | 치명 | ✅ |
| P2 | 버스 정책에 조건이 없어 등록된 계정이 **아무 이벤트나** 우리 버스에 넣을 수 있었다 | 높음 | ✅ |
| P3 | 조건을 붙이는 API가 **정책 전체를 교체**한다 — 순진하게 쓰면 고객사 추가 시 앞 고객사 권한 소멸 | 치명 | ✅ |
| P4 | 인제스트 룰이 `aws.cloudwatch` 전체를 받았다 | 낮음 | ✅ |
| P5 | 알람이 여러 리전에 있으면 두 번째 리전 스택이 **IAM 역할 이름 충돌로 실패** | 중간 | ✅ |

## P1 — 없는 버스를 가리키고 있었다

온보딩 템플릿의 `CentralAlertBusArn` 기본값이 `aws-monitoring-alert-prod`였는데,
**계정에 배포된 스택은 dev 하나뿐이고 그 버스는 존재하지 않는다.** 고객이 원클릭으로 배포했다면
전달 룰이 없는 버스를 타깃으로 잡고, EventBridge는 실패를 조용히 삼킨다. 알람은 계속 울리는데
우리에겐 아무것도 안 들어오고, 고객 화면은 비어 있는 상태가 된다.

- 기본값을 **없앴다**. 값을 반드시 넘겨야 한다 — 틀리면 조용히 사라지는 종류의 설정에 기본값을
  두면 안 된다.
- 원클릭 링크가 실재하는 dev 버스 ARN을 채워 준다.

### 결정 (2026-09-09): 당분간 dev 스택으로 받는다

고칠 것은 "dev냐 prod냐"가 아니라 **없는 버스를 가리킨 것**이었고, 그건 위에서 해결됐다.
실재하는 버스를 가리키면 이름이 무엇이든 정상 동작한다.

근거:

- **dev와 prod는 이름만 다르다.** 템플릿에서 `Environment` 파라미터가 쓰이는 곳은 전부 리소스
  이름 접미사다. 백엔드에서 환경으로 동작이 갈리는 곳은 `alarm_naming._alarm_name()` 하나뿐이고,
  그건 옛 이름 형식 알람을 지울 때 쓰는 호환용이라 현재 생성 경로에서 호출되지 않는다.
  → prod를 세워도 **테스트 신뢰도가 올라가지 않는다.**
- **화면과 데이터가 dev에 있다.** 고객사를 prod에 등록하면 알람은 prod로 들어오는데 화면은 dev를
  보고 있어 아무것도 안 보인다. 맞추려면 Amplify 환경변수 전환 + 고객사·계정 데이터 이전이 따로 필요하다.
- **이전 비용이 싸다.** 나중에 옮길 때 고객사 쪽 작업은 `CentralAlertBusArn` 파라미터 하나 바꾸는
  스택 업데이트뿐이다. IAM 역할 그대로, 재온보딩 없음. 우리 쪽 버스 권한은 계정 등록 시 자동으로 붙는다.
- dev에 상시 배포하지만 그 사이 들어온 이벤트는 유실되지 않는다 — 인제스트 룰에 DLQ가 붙어 있고
  EventBridge가 재시도하며, 쌓이면 DLQ 알람이 Slack으로 온다.

**prod를 세울 시점** (둘 중 하나면 착수):

1. 알람이 실제로 중요한 고객사가 붙을 때 (테스트가 아니라 운영)
2. dev 상시 배포를 멈출 때 (기능 개발이 일단락될 때)

그때 필요한 작업은 순서대로: ① `python scripts/deploy-backend-stack.py --all-artifacts --stack
aws-monitoring-engine-prod --environment production` (스크립트는 새 환경 생성을 지원한다, `1131f9d`)
② prod 버스 실재 확인 ③ 원클릭 링크의 버스 ARN 교체 ④ 공개 S3 템플릿 재업로드·3곳 동기화
⑤ prod에 고객사·계정 등록 ⑥ 화면을 prod로 옮길지 별도 판단.

## P2·P3 — 버스 정책

버스 정책은 "이 계정이 우리 버스에 이벤트를 넣어도 된다"만 말했다. 조건이 없으면 등록된 고객사
계정이 알람과 무관한 이벤트를 마음대로 밀어 넣을 수 있다. 이제 `events:source`(=`aws.cloudwatch`)와
`events:detail-type`(알람 상태 변경·구성 변경 2종)으로 제한한다.

**그런데 조건을 걸려면 `PutPermission`의 `Policy` 파라미터를 써야 하고, 그건 정책 전체를 교체한다.**
실측으로 확인했다: Sid가 다른 두 statement를 차례로 넣으면 뒤엣것만 남는다. 그대로 썼다면
두 번째 고객사를 등록하는 순간 첫 고객사의 알람이 그날부터 끊기고, 아무 오류도 나지 않는다.

그래서 등록·삭제 모두 **읽고 → 합치고 → 쓰기**다. 쓴 다음 다시 읽어 기존 Sid가 전부 남아 있는지
확인하고, 하나라도 없으면 `grant_failed`로 보고한다. 동시 등록이 서로를 지우는 경우를 조용히
넘기지 않기 위해서다.

**부작용 하나:** `Policy` 형식은 실재하지 않는 계정을 principal로 받지 않는다(`invalid principal`).
계정 ID를 잘못 입력하면 등록은 되지만 `alert_forwarding=grant_failed`가 뜬다. 예전 형식은
아무 12자리나 받아들였으므로, 이건 오타를 일찍 잡아 주는 쪽으로 바뀐 것이다.

## P4 — 룰 범위

중앙 인제스트 룰 2개와 고객사 전달 룰이 이제 같은 2종 detail-type만 받는다. 버스 정책 조건과
범위가 같아야 한다 — 룰이 더 넓으면 정책에서 거부되어 원인 모를 누락이 된다.

## P5 — 여러 리전

IAM 역할은 글로벌인데 EventBridge 룰은 리전 리소스다. 알람이 서울과 도쿄에 있으면 스택이 두 개
필요한데, 두 번째가 같은 역할 이름을 만들려다 실패한다. `CreateSharedRoles=no` +
`ExistingAlertForwardRoleArn`으로 두 번째부터는 룰만 배포한다.
