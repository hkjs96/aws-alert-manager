## 1. 지금 잘못 동작하는 것

### B1. dedup이 억제 20건 뒤에 풀린다 — `alert_ingestor._last_notified_at`

```python
resp = table.query(KeyConditionExpression=Key("series_id").eq(series_id),
                   ScanIndexForward=False, Limit=20)
for item in resp["Items"]:
    if not item["suppressed"]: return item["occurred_at"]
return None   # ← 최근 20건이 전부 억제된 것이면 "알린 적 없음"이 된다
```

**시나리오.** 알람이 1시간에 15번 토글한다(가장 흔한 노이즈).
첫 ALARM → NOTIFY. 이후 ALARM 14건은 dedup, OK 15건은 cleared — 전부 `suppressed=True`.
**10번째 토글부터 NOTIFY가 조회 창 밖으로 밀려나** 11번째 ALARM은 다시 NOTIFY다.
결과: 4시간 재알림 주기가 "10번 토글마다"로 바뀐다. 억제하려던 바로 그 알람에서.

**왜 생겼나.** "마지막으로 알린 시각"이라는 **상태**를 append-only **이력**에서 스캔으로 복원했다.
이력이 길수록 상태 복원이 비싸지고 불완전해지는 구조다. `Limit`을 키우는 것은 답이 아니다 —
100건 뒤에 같은 문제가 난다.

**처리 → D9.** 지문(fingerprint)별 상태 항목을 따로 둔다. 아래 [설계 정정](#8-설계-정정) 참조.

### B2. 미관리 알람이 한 파티션으로 몰린다 — `AlertEvent.series_id`

```python
return f"{self.account_id}#{self.resource_id}#{self.metric_key}"
# identify_alarm 실패 → resource_id="" → "111122223333##CPUUtilization" 또는 "111122223333##"
```

고객사 자체 알람(우리 메타데이터 없음)은 **계정 안에서 전부 같은 PK**를 갖는다.

- 그 계정의 미관리 알람 폭풍이 오면 파티션 하나에 쓰기가 몰린다(파티션 상한 1,000 WCU/s).
- dedup Query가 **다른 알람의** 이벤트를 돌려준다 → `last_notified_at`이 엉뚱한 알람의 것.

메타데이터가 없어도 이벤트에는 항상 `alarm_arn`이 있다. 해석 실패 시 `resource_id` 자리에
알람 ARN을 넣으면 키는 유일해지고 MetricHistory 조인 규약은 해석 성공 케이스에서 그대로 유지된다.

### B3. Phase 0 스크립트가 14일 넘는 창을 조용히 축소한다 — `scripts/analyze_alarm_history.py`

CloudWatch 알람 이력 보존은 **14일**이다. `--days 30`을 주면 API는 14일치만 돌려주는데,
스크립트는 `len(episodes) / 30`으로 나눈다 → **일당 발화율·flapping 판정이 최대 2배 과소**.
flapping 기준(3회/일)에 걸릴 알람이 안 걸린다.

처리: `--days`를 14로 클램프하고 경고 + 실효 창은 **응답의 가장 이른 항목**으로 계산.
그리고 2주 뒤부터는 EventHistoryTable(90일)이 이 스크립트의 데이터 소스가 되어야 한다 —
그게 이 테이블을 만든 이유 중 하나다.

## 2. 폭풍이 오면 무너지는 것

기준 봉투: 대시보드 실측이 하루 2,368건, 스파이크 ~20k. **10분에 5천~2만 건(8~33건/초)**을 견뎌야 한다.

### S1. 예약 동시성 없음 — 느린 하류가 계정 전체를 멈춘다

정상일 때는 문제없다: 33건/초 × 50ms = 동시 실행 ~2. Lambda는 충분하다.
문제는 **하류가 느려질 때**다. DynamoDB 스로틀이나 네트워크 지연으로 호출당 30초(타임아웃)까지
늘어나면 33 × 30 = **동시 1,000 = 계정 기본 한도 전부**. 그 순간부터 `api_handler`,
`daily_monitor`, `sqs_worker`가 스로틀된다. **장애 중에 UI가 죽는** 시나리오다.

처리: `ReservedConcurrentExecutions: 50`. 코드 변경 없음. 인제스터가 50을 넘으면 EventBridge가
재시도(24h, 185회)하므로 이벤트는 안 잃는다 — 늦어질 뿐이다. 늦는 것과 계정이 멈추는 것 중
늦는 쪽을 택한다.

SQS 버퍼(EventBridge → SQS → Lambda 배치)는 더 좋지만 인제스터를 배치 처리로 바꿔야 한다.
지금은 예약 동시성으로 막고, 배치 전환은 1.4.3 grouping과 함께 한다(어차피 그때 배치가 필요하다).

### S2. 이벤트 단위 타이머는 폭풍에서 실행 수가 폭발한다 — 1.4.2 설계 정정

tasks 1.4.2는 "DEFER → Step Functions Wait"인데, 이벤트마다 실행을 만들면 폭풍 한 번에
2만 실행이다. 비용은 ~$2.5/폭풍(감당 가능)이지만 `StartExecution` API 한도에 걸리고,
무엇보다 **auto-pause가 끝난 뒤 2만 개가 각자 알림을 보낸다** — 유예의 목적을 정면으로 어긴다.

Alertmanager 모델을 다시 보면 **grouping이 먼저**다: 첫 이벤트가 그룹(고객사×등급 등)을 열고
`group_wait` 동안 도착한 이벤트가 합류한 뒤 **알림 하나**가 나간다. auto-pause는 그 그룹에
붙는 더 긴 대기다. 즉 실행은 **그룹당 하나**이고, 이벤트가 실행에 "합류"할 필요도 없다 —
실행이 깨어날 때 이력 테이블에서 "이 그룹의 시작 이후 이벤트"를 읽으면 된다.

처리 → **D10**. 태스크 순서를 1.4.3(grouping) → 1.4.2(그룹 단위 타이머)로 뒤집는다.

## 3. 조용히 실패하는 것

### Q1. DLQ가 차도 아무도 모른다

`AlertIngestDLQ`에 알람이 없다. 인제스터가 망가지면 알람 이벤트가 조용히 DLQ에 쌓인다 —
**"기록되지 않은 알람"이 생기는데 그것을 알릴 경로가 없다.**

처리: DLQ `ApproximateNumberOfMessagesVisible ≥ 1` 알람 + 인제스터 `Errors`/`Throttles` 알람.
**반드시 `ErrorAlertTopic`(SNS)에 직결**한다. 우리 파이프라인을 태우면 "인제스터가 죽었다"는
알람이 죽은 인제스터로 가서 DLQ에 들어간다. 자기 감시는 감시 대상에 의존하면 안 된다.

### Q2. 계정→고객사 캐시가 컨테이너 수명 동안 고정이다

`_account_to_customer`는 `lru_cache`로 영구다. Lambda 컨테이너는 몇 시간을 산다.
새 고객사를 등록하면 그 계정의 이벤트는 컨테이너가 교체될 때까지 `customer_id=""`로 적재되고
`customer_day="#2026-…"`에 들어간다 → **고객사 리포트에서 보이지 않는다.**

처리: 5분 TTL. `daily_monitor`의 기존 캐시 패턴과 같다.

### Q3. `raw`가 8,000자에서 잘린다 — 잘리면 JSON이 아니다

`json.dumps(raw)[:8000]`. 알람 이벤트는 보통 1~3KB라 안 걸리지만 metric math 알람은
`configuration.metrics`가 커진다. 잘리면 `json.loads`가 실패해 재현(R2-5)이 불가능하고,
어느 항목이 잘렸는지 표시도 없다. DynamoDB 항목 한도는 400KB다.

처리: 상한 64KB로 올리고, 넘으면 `detail`만 보존 + `raw_truncated=True`. 잘라도 JSON은 유지한다.

## 4. Shadow 측정 해석 시 주의

지금 쌓이는 판정은 **완전한 엔진의 결과가 아니다**. `decide()`에 다음이 전달되지 않는다:

| 인자 | 현재 | 효과 |
|---|---|---|
| `is_flapping` | 항상 False | flapping 격리가 한 번도 발동하지 않는다 → 억제율 과소 |
| `already_notified` | 항상 False | 해소 전이가 항상 `SUPPRESS cleared` → 해소 알림 건수 0 |
| `policy.silences` | 빈 튜플 | 정비창 없음 |

따라서 **현재 억제율은 하한**이다. 리포트에 이 사실을 적어야 한다. 셋 다 D9 상태 테이블이
있어야 채울 수 있다.

> **→ 같은 날 1.4.2로 해소:** `is_flapping`·`already_notified`는 `AlertStateTable`에서 채운다.
> 남은 것은 `silences`뿐(1.4.4 저장소·UI). B1도 함께 해소 — 라이브 25번 토글에 발화 NOTIFY 1건.

**DEFER write-back.** 1.4.2가 붙으면 적재 시점 판정은 `defer`인데 유예 후 결과(억제/발송)는
이력에 기록되지 않는다. 그룹 실행이 끝날 때 해당 이벤트들의 `final_action`을 `UpdateItem`으로
써야 억제율 집계가 맞는다.

## 5. 발송을 붙이기 전에 반드시 (Phase 2 진입 조건)

### P1. 멱등성 — 같은 알림이 두 번 나간다

- EventBridge → Lambda는 **at-least-once**. 같은 이벤트가 두 번 올 수 있다. `put_item`은 같은
  키를 덮어쓰니 이력은 괜찮지만, **발송은 부작용**이라 두 번 나간다.
- 같은 series의 ALARM 두 건이 몇 초 간격으로 동시에 처리되면 둘 다 "알린 적 없음"을 보고
  둘 다 NOTIFY다(Query→Put이 원자적이지 않다).

처리: (1) 이력 put에 `attribute_not_exists(event_key)` 조건 — 실패하면 이미 처리한 이벤트이니
발송 없이 종료. (2) 상태 테이블의 `last_notified_at` 갱신을 조건부 `UpdateItem`으로 —
"내가 읽은 값이 아직 그대로일 때만" 갱신하고, 실패하면 남이 먼저 알린 것이니 dedup.
D9가 있어야 (2)가 가능하다.

### P2. 등급 소스 — 레지스트리 기본값이 바뀌면 기존 알람과 어긋난다

인제스터는 `get_severity(metric_key)`(레지스트리 기본값)를 쓴다. 알람의 `Severity` 태그도
생성 시 같은 함수로 썼고 API 오버라이드 경로가 없으니 **지금은 일치한다.** 어긋나는 경우는
레지스트리 기본값을 바꾼 뒤 재빌드되지 않은 기존 알람뿐이다.

SEV-1 면제(R3-8)가 이 값에 걸려 있으므로 낮게 볼 수는 없다. 가장 싼 해법: 생성 시
`AlarmDescription` 메타데이터 JSON에 `severity`를 넣는다(이미 `metric_key`/`resource_id`를
넣고 있다). 이벤트가 `configuration.description`을 싣고 오므로 추가 API 호출이 없다.
기존 알람은 다음 동기화 재빌드 때 반영된다.

## 8. 설계 정정

### D9. 상태와 이력을 분리한다 — `AlertStateTable`

**문제.** "마지막 알림 시각", "flapping 격리 여부", "이 발화에 알렸는가"는 **상태**다.
append-only 이력(EventHistoryTable)에서 스캔으로 복원하면 B1처럼 이력이 길수록 틀린다.

**결정.** 지문별 상태 항목을 따로 둔다.

```
AlertStateTable  PK: state_key
  fp#{fingerprint}    last_notified_at, episode_started_at, recent_episodes[≤30 ts],
                      quarantined_until, incident_id, version(조건부 갱신용)
  grp#{group_id}      execution_arn, opened_at, status        ← D10에서 사용
```

- 읽기 1회(`GetItem`)로 dedup·flapping·already_notified가 모두 결정된다. Query 스캔이 없다.
- `recent_episodes`로 `is_flapping(episode_count, window_days)`를 그대로 쓴다 — 실측 스크립트와 같은 식.
- 갱신은 `version` 조건부 — 동시 처리에서 한쪽만 이긴다(P1).
- TTL 30일: 한 달 조용한 알람의 상태는 없어도 된다(첫 발화처럼 다룬다).
- 비용: 이벤트당 GetItem 1 + UpdateItem 1. 월 7만 이벤트 기준 $0.1 미만.

이력 테이블은 그대로 **감사·재현·학습 데이터**로 남는다. 역할이 갈라진다.

### D10. 타이머는 그룹 단위다, 이벤트 단위가 아니다

**문제.** S2. 이벤트마다 Step Functions 실행을 만들면 폭풍에서 실행이 폭발하고 유예 후
각자 알림을 보낸다.

**결정.** 실행은 **그룹당 하나**. 그룹 키는 우선 `{customer_id}#{severity}`(Alertmanager 기본과
같은 축; U3에서 조정 가능).

```
첫 이벤트 → grp#{key} 없음 → StartExecution, grp# 기록
            grp#{key} 있음 → 이력만 적재 (실행에 합류시키지 않는다)

실행:  Wait(group_wait 30s)
     → 이력에서 opened_at 이후 이 그룹의 이벤트 조회
     → SEV별 auto_pause 있으면 Wait(pause) → 재조회, 해소된 것 제외
     → 남은 것으로 알림 1건 구성 → 발송(Phase 2)
     → 이벤트들의 final_action write-back, grp# 닫음
```

- 이벤트가 실행에 메시지를 보낼 필요가 없다 — 실행이 깨어날 때 이력을 읽는다. 단순하고 경쟁이 없다.
- 폭풍 2만 건 = 고객사×등급 조합 수만큼의 실행(수십 개). 전이 수백, 비용 센트 단위.
- auto-pause와 group_wait가 하나의 실행 안에서 순차로 처리된다. 타이머 두 종류가 아니다.
- tasks.md 1.4.2/1.4.3 순서와 내용을 이에 맞춰 고친다.
