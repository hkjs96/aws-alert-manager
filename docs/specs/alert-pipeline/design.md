# Design — 알림 파이프라인

> 조사일 2026-09-01. 요구사항은 `requirements.md`, 구현 계획은 `tasks.md`.

## 1. 계층 구조

```
   고객사 계정 (N개, 리전 M개)
   ┌──────────────────────────────────────┐
   │  CloudWatch 알람 (700+/계정)          │
   │        │ 상태 전이 · 생성/수정/삭제    │
   │        ▼                              │
   │  기본 이벤트 버스 (자동)               │
   │        │ EventBridge 룰 1개/리전       │
   └────────┼──────────────────────────────┘
            ▼  크로스 어카운트 + 크로스 리전
   우리 계정
   ┌──────────────────────────────────────────────────────────┐
   │ ① 수집    이벤트 버스 → 정규화 Lambda                     │
   │ ② 이력    EventHistoryTable  ← 정제 전 원본 전량          │
   │ ③ 정제    dedup → auto-pause → group → inhibit → silence │
   │ ④ 인시던트 Step Functions (생명주기 + 타이머)             │
   │ ⑤ 온콜    스케줄 조회 → 에스컬레이션                      │
   │ ⑥ 알림    채널 표 조회 → 조건 매칭 → 발송                 │
   │ ⑦ AIOps   규칙 진단 → (AI 요약) → Runbook L1/L2/L3       │
   └──────────────────────────────────────────────────────────┘
```

**핵심 원칙: 알람과 알림을 분리한다.** 알람은 "무엇을 감시하는가", 알림은 "누가 어떻게 받는가"다.
지금은 이 둘이 `AlarmActions`로 붙어 있어 한쪽을 바꾸면 다른 쪽 700개를 고쳐야 한다.

## 2. 설계 결정

### D1. 수집은 EventBridge로 — `AlarmActions`를 쓰지 않는다

**결정:** 고객사 계정의 기본 이벤트 버스에서 알람 이벤트를 우리 계정 버스로 포워딩한다.

**근거:**

AWS 문서 확인 사실:
> *"CloudWatch sends events to Amazon EventBridge whenever a CloudWatch alarm is **created, updated, deleted, or changes alarm state**."*
> *"CloudWatch **guarantees** the delivery of alarm state change events to EventBridge."*

| 항목 | AlarmActions (현재) | EventBridge (채택) |
|---|---|---|
| 리전 제약 | 같은 리전 SNS만 | 크로스 리전 지원 |
| 크로스 어카운트 | TopicPolicy 필요, 고객사마다 갱신 | 버스 정책 1회 |
| **알람 CRUD 시 설정 반영** | **알람마다 박음 → 드리프트** | **무관 — 룰이 패턴으로 커버** |
| 알람당 액션 수 | 최대 5개 | 무제한 |
| 알람 생성/삭제 감사 | 불가 | 이벤트로 수신 |
| 설정 지점 | 알람 700개 | 계정×리전당 룰 1개 |

요구사항 R1-2("알람 개수와 무관")를 `AlarmActions`로는 구조적으로 만족할 수 없다.
현재 겪고 있는 3중 차단(리전/계정/구독자) 중 앞의 둘이 원천 소멸한다.

**검증 필요:** 크로스 리전 포워딩은 "지원 목적지 리전" 제한이 있다. us-east-1이 목적지면 문제없을 가능성이 높으나 dev에서 엔드투엔드 프로브로 확인한다(tasks.md 1.1).

**비용:** 계정 간 이벤트 전달은 **보내는 쪽(고객사)** 에 custom event로 과금($1/100만).
고객사 1곳 월 1,420건 기준 $0.0014 — 알람 요금 $71 대비 무시 가능.

**기존 알람의 AlarmActions:** 비워도 되고 남겨도 무해하다(어차피 도달 불가). 혼란 방지를 위해
Phase 1 완료 후 정리하되, 알람 700개 수정이 필요하므로 드리프트 감지 경로를 통해 점진 반영한다.

### D2. 타이머는 Step Functions Standard로

**결정:** 인시던트 하나 = Step Functions 실행 하나. 생명주기 전체를 상태 기계로 표현한다.

**근거:** 이 기능의 핵심 동작이 전부 "기다렸다가 조건 확인"이다.

| 기능 | 타이머 |
|---|---|
| Auto-pause | 2~15분 후 여전히 ALARM인가 |
| Grouping | 30초 모으기 |
| 에스컬레이션 | 5분 무응답 → 다음 단계 |
| Ack 타임아웃 | 30분 미해결 → 재알림 |
| repeat_interval | 4시간마다 재알림 |

**대안 비교:**

| 수단 | 판정 |
|---|---|
| SQS delay queue | 최대 15분 — 에스컬레이션 불가 |
| DynamoDB TTL | 최대 48시간 지연 가능 — 정확도 부족 |
| EventBridge Scheduler one-time | 가능하나 상태 관리를 직접 해야 함 |
| **Step Functions Standard** | **최대 1년, Wait 상태, 실행 상태가 콘솔에서 시각화됨** |

> 로드맵에 "Step Functions 실익 없음"이라 적혀 있으나 그것은 **daily monitor 팬아웃** 맥락이다.
> 인시던트 생명주기는 정반대로 Step Functions가 겨냥한 용도다. 이 구분을 유지할 것.

**비용:** 상태 전이 $0.025/1,000 (무료 4,000/월).
정제 후 인시던트 240건/일 × 15전이 = 월 10.8만 전이 = **$2.70/월**.
정제 없이 전량이면 106만 전이 = $26.60/월 — **정제가 비용도 10배 줄인다.**

### D3. 채널 설정은 DB 표로, 알람에 박지 않는다

**결정:** `NotificationChannelTable`에 고객사별 채널을 행으로 관리하고, 라우터가 조회해 발송한다.

**근거:** R6-1(복수 채널), R6-5(알람 무수정 반영)는 알람에 주소를 박는 방식으로 불가능하다.
CloudWatch 알람당 액션 5개 제한도 상한이 된다.

```
| 고객사 | 채널명       | 유형     | 대상                  | 조건            |
|--------|-------------|---------|----------------------|----------------|
| A사    | 운영팀 슬랙  | slack   | (Secrets 참조)        | 전체            |
| A사    | 야간 당직    | webhook | (Secrets 참조)        | SEV-1·SEV-2    |
| B사    | DB팀 슬랙    | slack   | (Secrets 참조)        | RDS·DocDB      |
```

**AWS Chatbot 직결을 쓰지 않는 이유:** Chatbot은 **토픽 1개 = 채널 1개** 매핑이라
severity별 분기도 고객사별 분기도 불가능하다. `docs/ALARM-RULES.md` §334-337의 SEV별 라우팅
요구를 만족하려면 (고객사 × severity)만큼 토픽이 필요해진다. 코드 라우터가 필수다.

**자격증명:** Webhook URL은 Secrets Manager에 저장하고 표에는 참조만 둔다(R6-8).

### D4. 정제 기법은 Alertmanager + PagerDuty 모델을 따른다

업계 조사 결과, 노이즈 감소 기법은 아래로 수렴한다. Alertmanager 기본값을 출발점으로 삼는다.

| 기법 | Alertmanager 기본값 | 우리 적용 |
|---|---|---|
| Deduplication | fingerprint 기준 | 알람 ARN + 상태 |
| Grouping | `group_wait 30s`, `group_interval 5m` | 동일 (고객사·계정·리소스타입·메트릭으로 group_by) |
| Repeat | `repeat_interval 4h` | severity별 조정 |
| Inhibition | source/target matcher + `equal` | 리소스 관계 태그(`_lb_arn`, `_cluster_name`)로 **자동 생성** |
| Silence | `mute_time_intervals` | 정비창 설정 |
| **Auto-pause** | (PagerDuty 고유, 2~15분) | severity별 유예 |

**Auto-pause를 최우선으로 두는 이유:** PagerDuty가 노이즈 감소의 1순위로 제시하는 기법이며,
CloudWatch가 ALARM→OK 전이를 보장 배달하므로 "타이머 걸고 OK 오면 취소"로 단순 구현된다.
High 1,687건 중 자동 해소되는 비율이 클 것으로 추정되나 **실측 전까지는 가설**이다(tasks.md 0.1).

**Inhibition의 우리 강점:** Alertmanager는 사람이 룰을 손으로 쓴다. 우리는 인벤토리에
리소스 관계가 이미 태그로 들어 있어 룰을 자동 생성할 수 있다.

**알람쪽 vs 알림쪽 억제:** 이미 SEV별 M-of-N(알람쪽)이 있다. 둘은 겹치지 않고 쌓인다.
- 알람쪽에서 참으면 → 조정 시 알람 700개 수정
- 알림쪽에서 참으면 → 설정 1줄 수정

따라서 **조정이 잦은 억제는 알림쪽에 둔다.**

### D5. 분석은 규칙 80% + AI 20%

**결정:** 사실 수집은 규칙으로, 요약·추론만 AI로 한다.

**근거:** 진단에 필요한 재료를 이미 보유하고 있다.

| 보유 데이터 | 답하는 질문 |
|---|---|
| `MetricHistoryTable` (91일 일별 p50~p99) | 평소엔 얼마였나 |
| `ResourceInventoryTable` (리소스·태그·관계) | 뭐고 누구 건가, 뭐랑 연결됐나 |
| `threshold_at_time` (스냅샷 기록 중) | 그때 임계치는 얼마였나 |
| CloudTrail (remediation_handler 수신 중) | 최근 누가 뭘 바꿨나 |
| `EventHistoryTable` (신규) | 이 알람의 과거 패턴은 |

규칙만으로 나오는 출력 예시:

```
🔴 [EC2] web-01 CPUUtilization 92% > 80%
  평소     : p99 45%, 최대 71% (28일)
  최근 변경 : 2시간 전 t3.medium → t3.small (CloudTrail)
  동시 발생 : 같은 ALB 뒤 3대 중 2대
  이 알람   : 지난 7일 23회 발화, 평균 4분 만에 자동 해소
```

AI는 마지막 "추정 원인 / 권장 조치" 두 줄에만 쓴다. R7-6(근거 제시 가능)을 만족하며,
Anomaly Detection을 "설명 불가"로 기각한 기존 결정과 일관된다.

**AI 비용 통제 — 패턴 단위 호출:** 인시던트마다 호출하지 않는다.
`(리소스타입 × 메트릭 × severity)` 패턴 서명으로 캐싱하여 새 패턴만 분석한다.
- 인시던트 단위: 월 7,200회 → 약 $40
- **패턴 단위 + 프롬프트 캐싱: 월 1,500회 → 약 $5**

### D6. 조치는 L1 → L2 → L3 순으로만 확장한다

| 단계 | 예 | 사람 개입 | 도입 |
|---|---|---|---|
| **L1 진단** | 로그 조회, 프로세스 목록, 디스크 사용량 | 없음 | Phase 4 초기 |
| **L2 원클릭** | Slack 버튼 → 재시작·스케일아웃 | 승인 필수 | Phase 4 후기 |
| **L3 자동** | 조건 충족 시 자동 실행 | 없음 | 별도 판단 |

**L1부터 시작하는 이유:** 읽기 전용이라 위험이 없고, 그것만으로 "알람 보고 접속해 확인"하는
단계가 사라진다. PagerDuty도 액션을 Diagnostics / Remediation 두 범주로 나눈다.

**실행 수단은 SSM Automation.** AWS 관리형 runbook이 다수 존재하고, 승인 단계(`aws:approve`)가
내장이며, 실행 이력이 남는다. 스텝당 $0.002.

**기존 `remediation_handler`와 분리(R8-7):** 그 모듈은 *"승인되지 않은 리소스 변경 감지 → EC2/RDS 정지"*
라는 거버넌스 기능이다. 인시던트 조치와 목적·위험도가 다르므로 이름과 코드를 섞지 않는다.

## 3. 외부 도구 조사 결과 — 채택하지 않음

| 후보 | 온콜 | 정제/라우팅 | AIOps | 판정 |
|---|---|---|---|---|
| **Prometheus Alertmanager** | ❌ | ✅ 표준 모델 | ❌ | **미채택** — 상태 유지형 상시 구동 필요 → Fargate 고정비 월 $10~15(현 총비용의 40배). 설정이 YAML 파일이라 고객사별 UI 관리 불가 |
| **Keep** (MIT, CEL 상관규칙) | ❌ | ✅ | ✅ | **보류** — 좋은 후보지만 컨테이너+DB 상시 구동. 규모 확대 시 재검토 |
| **Grafana OnCall** | ✅ | — | — | **불가** — 2026-03-24 아카이브(읽기 전용) |
| **AWS SSM Incident Manager** | ✅ | 부분 | ❌ | **불가** — *"no longer open to new customers"*. AWS는 OpsCenter($2.97/1,000 OpsItem) 안내하나 그것은 티켓 관리이지 온콜이 아님 |
| **GoAlert** (Target, Go 단일바이너리+PostgreSQL) | ✅ 특화 | 약함 | ❌ | **온콜 한정 후보** — 멀티테넌트 지원 여부 확인 필요 |
| **PagerDuty AIOps** | ✅ | ✅ | ✅ | **미채택** — 사용자당 과금(정확한 단가 미확인, 도입 검토 시 견적 필요). 고객사별 라우팅에 서비스를 고객사 수만큼 필요 |

**공통 기각 사유: 전부 상시 구동 컴퓨트를 요구한다**(R10-1 위반). 현 시스템은 전 구간 서버리스이며
실측 운영비가 월 $0.35다(`docs/reports/COST-IMPACT-2026-08-31.md`). 상용 SaaS는 사용자당 과금이라
관제 인원에 비례해 늘어나는 반면, 직접 구현은 이벤트 수에 비례하며 그 비용이 §4처럼 훨씬 낮다.

**Incident Manager 차단이 아프다.** 인시던트+온콜+에스컬레이션+runbook을 AWS 네이티브로 제공하던
유일한 후보였다. 온콜(⑤)은 직접 구현하거나 GoAlert를 붙이는 수밖에 없다.

## 4. 비용 종합

실측 트래픽(2,368 알람/일, 정제 후 인시던트 240건/일 가정) 기준 **우리 계정** 월 비용:

| 계층 | 항목 | 월 |
|---|---|---|
| ① 수집 | 이벤트 버스 수신(수신 계정 무과금) + 정규화 Lambda | $0 (무료 구간) |
| ② 이력 | DynamoDB 쓰기 + 저장(TTL 90일) | $0.10 |
| ③ 정제 | Lambda | $0 (무료 구간) |
| ④ 인시던트 | Step Functions 10.8만 전이 | $2.70 |
| ⑤ 온콜 | Lambda + DDB | $0.05 |
| ⑥ 알림 | Lambda + 전송(무료 100GB) + Secrets Manager | $0.45 |
| ⑦ AIOps | AI 패턴 분석 $5 + SSM Automation $6 | $11 |
| | **합계** | **약 월 $15** |

고객사 계정 추가 부담: EventBridge 계정 간 전달 **월 $0.0014/고객사** (알람 $71 대비 0.002%).

**비교:** 현 시스템 실측 월 $0.35 → 약 $15로 증가. 상용 SaaS(사용자당 과금)와 달리 관제 인원이 늘어도 비용이 늘지 않는다.
R10-4(월 $50 이내) 충족.

|---|---|---|---|
| **U1** | **온콜의 축** — 우리 관제팀 단일 로테이션인가, 고객사별 개별 온콜인가 | 전자면 GoAlert 등으로 대체 가능. 후자면 멀티테넌트 온콜 직접 구현 → Phase 3 규모 수배 | Phase 3 착수 전 |
| **U2** | **채널 등록 주체** — 우리가 대행 vs 고객사 직접 | 후자는 고객사 로그인·권한 체계가 선행 (현재는 MSP 내부 도구라 고객사 계정 개념 없음) | Phase 2 착수 전 |
| **U3** | **조건(필터) 범위** — severity만 / +리소스타입 / +계정·시간대 | 데이터 모델 복잡도 | Phase 2 착수 전 |
| **U4** | **멀티클라우드 범위** — AWS 외(Azure/GCP/KTC/NCP…)를 이 파이프라인이 다루는가 | 기존 관제 대시보드는 9개 프로바이더를 다룸. ①수집 어댑터만 추가하면 되도록 스키마를 클라우드 중립으로 설계(R1-6) | 설계 단계에서 대비, 구현은 후순위 |
| **U5** | 크로스 리전 EventBridge 포워딩의 목적지 리전 제한 | D1 전제 | Phase 1 첫 태스크에서 실측 |
