# EC2 애플리케이션 상태 검사 (2026-09-08)

AWS가 2026-08에 낸 **application status checks**를 이 제품에 어떻게 들일지. 출처는
`https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/application-status-checks.html`.

## 1. 기능 사실 (문서 확인)

AWS가 VPC 안에 **관리형 ENI**를 만들어 인스턴스의 앱 엔드포인트로 60초마다 HTTP/HTTPS 요청을
보내고 응답 코드로 정상 여부를 판정한다. 인스턴스에 에이전트를 설치하지 않는다.

| 항목 | 값 |
|---|---|
| 주기 | 60초 **고정**(변경 불가) |
| 판정 | 연속 실패 2회 → impaired, 연속 성공 2회 → 정상 (각각 조정 가능) |
| 타임아웃 | 기본 6초 (1~30) |
| 정상 코드 | 기본 `200` (matcher) |
| 경로·포트 | 기본 `/`, 포트 지정 |
| 기동 유예 | `InitializationGracePeriodSeconds` 기본 300초 (1~600) |
| 프로토콜 | HTTP/2로 보냄. HTTPS는 **서버 인증서를 검증하지 않는다** |
| 집계 | `included`(기본) / `excluded` |
| 연결 | 인스턴스 ID 또는 **태그**로 연결 (`aws:autoscaling:groupName`으로 ASG 전체) |
| CFN | `AWS::EC2::ApplicationStatusCheck` |

**지표.** `StatusCheckFailed_Application` (AWS/EC2, `InstanceId`) — `included` 검사들을 인스턴스
단위로 집계한 0/1. 검사별 `StatusCheckFailed_Application_<check-id>`도 발행된다.
검사가 연결되지 않은 인스턴스는 **이 지표를 아예 발행하지 않는다.**

**비용.** 관리형 ENI **AZ당 시간 $0.01** (≈ 월 $7.3/ENI). ENI는 (소스 서브넷 × 보안 그룹) 조합마다
하나다 — 인스턴스 수가 아니라 **조합 수**에 비례한다. 200대가 서브넷 2 × SG 1이면 ENI 2개(월 $14.6),
서브넷 2 × SG 3이면 최대 6개(월 $44). 여기에 CloudWatch 알람 요금이 붙는다.

**한도.** 계정당 검사 50개, 검사당 연결 50개, 계정당 연결 200개, **대상 5,000개**(초과분은
그냥 모니터링되지 않는다 — 조용한 누락). 관리형 ENI는 리전당 네트워크 인터페이스 한도(AZ별 적용)를 먹는다.

**ASG 연동.** `included` 검사가 impaired면 ASG가 인스턴스를 **종료·교체**한다. 별도 설정 없이 그렇게 된다.

## 2. 두 갈래 — 소비와 프로비저닝

이 기능을 제품에 들이는 방식은 성격이 완전히 다른 둘로 갈린다.

**A. 소비(consume)** — 고객이 만들어 둔 검사의 결과를 우리가 알람·알림으로 다룬다.
`StatusCheckFailed_Application`은 그냥 CloudWatch 지표라 기존 엔진이 그대로 처리한다.
알람 → EventBridge → 인제스터 → 정제 → 그룹 → (Phase 2) Slack 경로를 공짜로 탄다.

**B. 프로비저닝(provision)** — 검사 자체를 우리가 만들고 연결한다. 새 AWS 리소스 타입이고,
온보딩 IAM·검사 정의 저장소·API·UI·한도 관리·배포 중 억제(suppression)가 전부 필요하다.

**이번에 한 것은 A뿐이다.** B는 아래 §5에 설계만 남긴다.

## 3. 구현 (A, 2026-09-08)

`StatusCheckFailed_Application`을 EC2 알람 레지스트리에 추가하되 **옵트인**이다.

- **옵트인 이유.** 검사가 없는 인스턴스는 지표를 발행하지 않으므로 기본 생성하면 전 인스턴스에
  영원히 데이터 없는 알람이 하나씩 생긴다. 알람 요금(개당 월 $0.10)만 늘고 얻는 게 없다.
  EC2 200대면 월 $20이 조용히 붙는다.
- **켜는 법.** 인스턴스에 `Threshold_StatusCheckFailed_Application` 태그를 붙인다(값은 0).
  `off`로 두면 기존 알람이 삭제된다 — 다른 지표와 같은 규칙. 리소스 상세 화면의 메트릭 설정에
  체크 해제 상태로 노출되므로 UI에서 켤 수 있다.
- **등급 SEV-1.** 앱이 응답하지 않는 것은 가용성 직결이다. `StatusCheckFailed`(시스템)와 같은 급.
  SEV-1은 M-of-N 평가 정책에서 제외되어 즉시 평가되고, 알림 파이프라인에서 **어떤 억제도 받지 않는다**
  (R3-8 면제) — 폭풍 중에도 묻히지 않는다.
- **`treat_missing_data: notBreaching`.** 여기가 이 알람의 핵심이다. 시스템 상태 검사(`StatusCheckFailed`)는
  `breaching`이지만 이건 반드시 `notBreaching`이어야 한다. 검사가 연결되지 않은 인스턴스는 지표가
  없고, `breaching`이면 그 인스턴스 전부가 즉시 알람이 된다.
- **평가 1분 1회.** 지표가 1분 주기이고 디바운스(연속 2회 실패)는 AWS 검사 쪽에 이미 있다.
  우리가 또 M-of-N을 얹으면 감지가 2배 늦어진다.
- **동적 알람과의 충돌 차단.** `_HARDCODED_METRIC_KEYS["EC2"]`에 넣어 `Threshold_` 태그가
  동적 알람 경로로도 잡혀 같은 알람이 두 벌 생기는 것을 막는다.

## 4. 주의할 것 (문서의 경고 + 우리 맥락)

- **`/health`가 공유 자원을 보면 전멸한다.** DB 연결까지 검사하는 `/health`는 DB 한 번 흔들릴 때
  모든 인스턴스가 동시에 impaired가 되고, `included` + ASG면 **함대 전체가 교체된다.** AWS 문서가
  명시적으로 경고한다. 고객에게 안내할 때 이 한 줄이 제일 중요하다. ASG 인스턴스 유지 정책으로
  동시 교체 수를 제한하도록 권고한다.
- **우리 알람은 그 파도를 먼저 보여준다.** 인스턴스 단위 SEV-1 알람이 동시에 수십 개 뜨면
  파이프라인이 고객사×SEV-1 그룹 하나로 묶어 한 번에 보낸다(D10) — 이 기능이 그대로 쓸모가 된다.
- **배포 중 오탐.** 배포·패치 중에는 검사가 실패한다. AWS는 `enable-application-status-check-suppression`
  (기간 지정)을 제공한다. 우리 정비창(silence)은 **알림만** 막고 ASG 교체는 못 막는다 — 배포 훅에서
  AWS 억제를 호출해야 한다. 둘은 다른 층이다.
- **권한은 변경 통제 대상.** `ec2:CreateApplicationStatusCheck`, `Associate…`, `Modify…`,
  `Enable…Suppression`은 인스턴스 가용성에 직접 영향을 준다(ASG 교체를 좌우). AWS 문서가 일반 EC2
  권한과 묶어 주지 말라고 권고한다 — B를 하게 되면 온보딩 역할에 넣을지부터 따로 판단해야 한다.
- **HTTPS 인증서 미검증.** 만료·오설정 인증서는 이 검사로 안 잡힌다. ACM 만료 알람(`DaysToExpiry`)이
  별도로 있어야 한다 — 우리는 이미 있다.

## 5. B(프로비저닝)를 한다면 — 미착수, 결정 필요

권한과 비용이 붙고 잘못하면 **인스턴스가 교체되는** 작업이라 A와 같은 무게로 다루면 안 된다.

1. **온보딩 IAM 확장** — 위 4개 액션. 변경 통제 권고 때문에 "우리가 대신 만들어 준다"가 옳은지부터 결정.
2. **검사 정의 저장소 + API** — 프로토콜·포트·경로·정상 코드·임계·유예. 고객사별.
3. **연결 전략** — 인스턴스 ID보다 **태그 연결**이 낫다(ASG 스케일아웃이 자동 포함).
   `Monitoring=on`에 붙이면 우리 태그 체계와 그대로 맞는다.
4. **안전 기본값** — 새 검사는 반드시 `aggregation=excluded`로 만들어 ASG 교체를 유발하지 않고,
   실측 뒤 사람이 `included`로 승격한다. AWS 문서의 권장 절차와 같다.
5. **한도·비용 가드** — 계정당 검사 50/연결 200/대상 5,000. 대상 초과는 조용히 누락되므로
   `AWS/Usage` 기반 알람이 필요하다. ENI 비용은 서브넷×SG 조합 수로 미리 계산해 보여줘야 한다.
6. **배포 억제 연동** — 고객 CI/CD 훅에서 억제를 켜고 끄는 경로.

**추천:** A를 먼저 굴려 실제 수요를 본 뒤 B를 판단한다. B는 "모니터링 도구"가 "가용성을 좌우하는
도구"로 성격이 바뀌는 지점이라, 고객 승인 없이 진행할 일이 아니다.
