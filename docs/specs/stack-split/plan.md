# 스택 분리 — 고객을 감시하는 스택과 자동 배포 스택을 나눈다 (계획, 2026-10-19)

상태: **계획 — 승인 대기**. 승인 전에는 아무것도 만들지 않는다.

## 왜

`aws-monitoring-engine-dev` 스택이 실제 고객 계정(HOME, 771283576189)을 감시한다. 이름은 dev지만 사실상 운영이다.
최근 장애 두 건이 모두 여기서 났다.

| 날짜 | 장애 | 원인 |
|---|---|---|
| 10-12 07:32 | 고객 바스티온의 우리 알람 4개가 약 21분간 사라짐 | 리전 순회 첫 실행의 버그가 배포 직후 고객 계정에 닿음 |
| 10-12 10:26 | 워커가 시작부터 죽고 정합 런 1회 유실 | 편집 중인 코드가 자동 배포됨 |

배포는 이제 검증을 통과한 커밋만 나간다(`bc9f816`). 그래도 "테스트는 통과했지만 실제 계정에서 틀리는" 버그가 있다.
10-12 07:32 장애가 그 경우다. 이런 버그는 고객 계정에 닿기 전에 걸러야 한다.

## 결정된 것

- **프론트는 하나를 그대로 쓴다**(사용자 결정 10-19). Amplify 앱 `d2ssyfndl4orxp`는 지금처럼 현재 스택의 API를 본다.

## 제안

프론트가 현재 스택을 보므로, **현재 스택을 고객 운영용으로 두고, 자동 배포는 새 실험 스택으로 옮긴다.**

| | 현재 스택 `aws-monitoring-engine-dev` | 새 실험 스택 `aws-monitoring-engine-stg` |
|---|---|---|
| 역할 | 고객 운영(이름은 유지) | 자동 배포 착지점, 실제 AWS에서 검증 |
| 감시 대상 | 지금 그대로(중앙 계정 + HOME) | **없음** — 정기 실행 끔 |
| 배포 | **수동**: 실험 스택에서 확인한 커밋만 `deploy_verified.py promote <sha>` | `main` 푸시 시 자동(지금의 pre-push 흐름) |
| 프론트 | 연결됨 | 연결 안 함(API로 직접 확인) |
| 데이터 | 기존 테이블 | 별도 테이블(`-stg` 접미사, 템플릿이 이미 환경별로 이름을 나눔) |

### 실험 스택이 정기 실행을 하지 않아야 하는 이유

두 스택이 같은 계정을 관리하면 알람 이름과 `ManagedBy=AlarmManager` 태그가 같다. 그래서 서로의 알람을 "내 것"으로
보고 고치거나 지운다. 실험 스택에는 다음을 둔다.

- 새 템플릿 파라미터 `ScheduledRuns` (`enabled` | `disabled`, 기본 `enabled`)
- 실험 스택은 `disabled`로 배포한다. 이 값이면 매일·매시·주간 스케줄과 배포 직후 동기화(`InitialAlarmSync`)를 만들지 않는다(CloudFormation Condition).
- 계정 테이블은 비워 둔다. 오케스트레이터는 테이블이 비면 중앙 계정 자신으로 폴백하므로, 스케줄을 끄는 것이 필수다.

검증은 실험 스택 API를 직접 호출해서 한다(연결 테스트, 중복 점검 등 읽기 위주). 알람을 실제로 만들어 보려면
`alarm_sync_dryrun.py`의 `RecordingCloudWatch`(쓰기를 가로챔)로 고객 계정을 대상으로 돌린다. 이 방식은 10-12 장애 때
배운 대로다.

### 배포 흐름(바뀐 뒤)

1. `git push` → pre-push가 깨끗한 사본에서 테스트하고, 통과하면 **실험 스택**에 자동 배포한다.
2. 실험 스택에서 스모크를 돌린다. 람다 오류 0, 핵심 API 응답, 필요하면 고객 계정 드라이런.
3. `python scripts/deploy_verified.py promote <sha>` → 같은 커밋을 **고객 운영 스택**에 배포한다.
   - 실험 스택에 배포된 적 없는 커밋은 거부한다(마지막 실험 배포 SHA를 기록해 비교).

## 고객에게 필요한 것

**없다.** 고객 역할(`AlarmManagerMonitoringRole`)은 중앙 계정 root를 신뢰하고, 이벤트 버스는 고객 운영 스택 것을
그대로 쓴다. HOME 고객의 스택 업데이트는 필요 없다.

## 작업 순서

1. 템플릿: `ScheduledRuns` 파라미터와 Condition. 스케줄 4개와 `InitialAlarmSync`에 적용한다. 기본값이 `enabled`라 현재 스택은 동작이 바뀌지 않는다.
2. 배포 스크립트: `deploy_verified.py`의 자동 배포 대상을 실험 스택으로 바꾸고, `promote` 명령을 추가한다.
3. 실험 스택 최초 생성(`ScheduledRuns=disabled`). 생성 후 스케줄 0개, 계정 테이블 0행, 람다 오류 0을 확인한다.
4. 문서: AGENTS.md 배포 절차, OPERATIONS.md, 메모리.

## 비용

실험 스택은 람다·DynamoDB 온디맨드·API Gateway라 쓰지 않을 때는 거의 0이다. 상시 비용은 CloudWatch 로그 보관 정도로 월 1달러 미만으로 추정한다(추정이며 측정 전).

## 열린 질문

- **이름:** 현재 스택 이름은 `-dev`로 남는다. 이름을 바꾸려면 스택을 새로 만들어야 하고, 그러면 테이블·버스·API 주소가 바뀌고 고객 버스 설정도 바뀐다. 그래서 이름은 그대로 두고 문서로 "dev = 고객 운영"을 명시하는 것을 제안한다.
- **실험 스택 위치:** 같은 계정(949501913924)에 둔다고 가정했다. 별도 계정이 있으면 더 안전하다(계정 경계로 분리).
